## 1. Decisions

| Question | Decision |
| --- | --- |
| Duplicate `inventory_item_id` in one order | Merge into the first occurrence, keeping request order, and sum quantities. |
| Merged quantity above the per-line cap (10,000) | Reject with 422 at `("items",)`. Never truncate. |
| Empty order | Rejected by `min_length=1` on `items`. |
| More than 100 lines | Rejected by `max_length=100` before merging. |
| PATCH semantics | Omitted = unchanged; explicit `null` clears only `description`. |
| Name normalization | Strip ends (T05) and collapse internal whitespace runs (T06). |
| Stock availability and SKU uniqueness | Not schema rules. They stay in the service/transaction layer (T14). |

## 2. Validators

**Field-level normalization.** `InventoryReplace.normalize_name` is a
`@field_validator("name")` that collapses internal whitespace after the
`Name` annotation has stripped the ends. `InventoryCreate` inherits it.
`InventoryPatch.normalize_name` does the same and passes `None` through, so an
explicit `null` name still fails the patch's null check rather than being
normalized.

**Field-level business rule.** `OrderCreate.merge_duplicate_lines` is a
`@field_validator("items", mode="after")`. It sums quantities per item, rejects
any total above `MAX_LINE_QUANTITY`, and returns the merged lines. It is
declared on `items` rather than as a model validator so that a rejected total
is reported at `("items",)`. A model validator raising `ValueError` reports at
an empty location, which is less useful to a client.

**Cross-field rules.** `InventoryPatch.validate_changes` (a
`@model_validator(mode="after")`, from T05) rejects an empty PATCH and any null
field other than `description`. It relies on `model_fields_set`, so it can tell
omitted fields from explicit nulls.

## 3. Strict and coercible inputs

| Input | Result | Why |
| --- | --- | --- |
| `quantity: 3` | accepted | Strict int. |
| `quantity: "3"`, `2.0`, `true`, `null` | rejected | Strict mode never coerces quantities, stock, prices, or IDs. |
| `sku: "  ab-1 "` | `"AB-1"` | Normalized by the `Sku` annotation (T05), not by coercion. |
| `name: "  Blue \t  Widget "` | `"Blue Widget"` | Strip plus internal whitespace collapse. |
| `name: "   "` | rejected | Empty after stripping fails `min_length=1`. |

## 4. PATCH and `model_dump()`

`InventoryPatch(stock=5).model_dump(exclude_unset=True)` returns `{"stock": 5}`.
Without `exclude_unset`, every unsent field appears as `None`, and a service
that applied that dump would clear `name`, `unit_price_minor`, and others. The
inventory service uses `exclude_unset=isinstance(body, InventoryPatch)`
(`app/services/inventory.py`), so PATCH applies only supplied fields. An explicit
`description: null` survives the dump as `{"description": None}`, which is
how a client clears it.

Pydantic v1 equivalents:

| Pydantic v2 (used here) | Pydantic v1 |
| --- | --- |
| `model_dump()` | `dict()` |
| `model_dump(exclude_unset=True)` | `dict(exclude_unset=True)` |
| `model_fields_set` | `__fields_set__` |
| `model_validate(data)` | `parse_obj(data)` |
| `@field_validator` | `@validator` |
| `@model_validator(mode="after")` | `@root_validator` (post) |
| `model_config = ConfigDict(...)` | inner `class Config:` |
| `from_attributes=True` | `orm_mode = True` |

## 5. Structured 422 responses

The app's handler (`app/api/errors.py`) keeps only `loc`, `msg`, and `type`
for each error and drops the submitted value. Example from
`POST /api/v1/inventory` with `name: "   "` and `unit_price_minor: "12500"`:

~~~json
{
  "detail": [
    {"loc": ["body", "name"], "msg": "String should have at least 1 character", "type": "string_too_short"},
    {"loc": ["body", "unit_price_minor"], "msg": "Input should be a valid integer", "type": "int_type"}
  ]
}
~~~

The tests assert that the submitted values (`12500`, the blank name) do not
appear in the response body. Other locations exercised: `("body",)` for an
empty PATCH, `("path", "item_id")` for `/inventory/0`, `("body", "items")` for
an over-cap or empty order, and `("body", "items", 0, "unit_price_minor")` for
an extra field inside an order line.

Order routes still return 501 (T14 implements them). The order-level 422 cases
are therefore tested on a probe route in `tests/test_t06_validation.py` that
uses the same handler.

## 6. Database-dependent rules

The schemas contain no stock, uniqueness, or existence checks. Those need the
database and belong in the service/transaction layer:

- stock availability for each merged line (T14, with a locking or conditional
  update strategy);
- SKU uniqueness (currently enforced by the in-memory store, to be a database
  constraint in T13);
- inventory item existence for each order line (T14).

Schema validation runs first and rejects malformed input cheaply. Business
checks run afterwards inside the transaction.
