## 1. Prerequisite review and gaps

| Topic | Reviewed behavior | Application to this project |
| --- | --- | --- |
| Type hints | Parameter/return annotations describe expected types. Python does not enforce them automatically. Understand `list[int]`, `int | None`, and `Annotated[T, metadata]`; accepting None and supplying a default are separate decisions. | FastAPI/Pydantic will interpret annotations and perform request validation. A positive quantity still needs a constraint. |
| Decorators | `@decorator` applies a callable to a function at definition time. A wrapper can run before/after calls; `functools.wraps` preserves identifying metadata. | Route decorators register handlers. Applying a decorator does not itself run the handler body. |
| Context managers | `with` manages enter/exit; `try/finally` protects cleanup when the body fails. Async managers use `async with` and awaitable enter/exit. | Database sessions and shared clients require explicit ownership and cleanup. |
| Generators | Calling a function containing `yield` creates an iterator; execution advances on iteration. Values are produced lazily. | HTTP methods | GET reads; POST creates/performs an operation; PUT replaces writable state; PATCH applies a partial change; DELETE removes the resource from active use. | Routes, request bodies, and status codes must express the agreed behavior below. |
| HTTP semantics | Safe methods request no state change. Idempotence concerns repeated effects, not identical response codes; PUT and DELETE are idempotent, while POST generally is not. ### Demonstration

This standalone, standard-library-only example was executed with `python -B -c` on the available Python 3.15.2 interpreter. The example intentionally passes a string to an integer annotation to demonstrate that the runtime does not validate that hint. It is a learning exercise, not an API validator.

~~~python
from collections.abc import Iterator
from contextlib import contextmanager
from functools import wraps

events: list[str] = []

def traced(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        events.append("called")
        return function(*args, **kwargs)
    return wrapper

def quantities(values: list[int]) -> Iterator[int]:
    for value in values:
        if value <= 0:
            raise ValueError("quantity must be positive")
        yield value

@contextmanager
def resource() -> Iterator[str]:
    events.append("acquired")
    try:
        yield "session"
    finally:
        events.append("released")

@traced
def total(values: list[int]) -> int:
    return sum(quantities(values))

def echo(value: int) -> int:
    return value

assert total([2, 3]) == 5
assert total.__name__ == "total"
assert echo("unchecked") == "unchecked"  # Deliberately violates the hint.
lazy = quantities([2, 0])
assert next(lazy) == 2
try:
    next(lazy)
except ValueError:
    events.append("invalid quantity")
else:
    raise AssertionError("validation was skipped")
try:
    with resource() as session:
        assert session == "session"
        raise RuntimeError("handler failed")
except RuntimeError:
    pass
assert events == ["called", "invalid quantity", "acquired", "released"]
print("PASS: type hints, decorator, lazy generator, exception-safe cleanup")
~~~

Observed result: `PASS: type hints, decorator, lazy generator, exception-safe cleanup`.

## 2. Domain model and order lifecycle

### Shared conventions

- Resource IDs are server-generated positive integers; timestamps are timezone-aware UTC values serialized as ISO 8601 strings ending in `Z`.
- Money uses integer minor units in a single currency, `INR`; `12500` means INR 125.00. Prices, line totals, and order totals never use binary floating point.
- Roles are `customer` and `admin`. Accounts are provisioned through a controlled local/test path in T15; public registration and user administration endpoints are outside this baseline.
- Historical orders and their line snapshots are retained. Inventory deletion means deactivation; SKU values cannot be changed or reused.

### Entities

| Entity | Fields and invariants |
| --- | --- |
| User | `id` PK; `username` unique after stripping outer whitespace and lowercasing (3-64 ASCII characters matching `[a-z0-9][a-z0-9_.-]{2,63}`); private `password_hash`; `role`; `is_active`; `created_at`, `updated_at`. Never store plaintext passwords. |
| InventoryItem | `id` PK; unique immutable `sku`; trimmed `name` (1-120 characters); nullable `description` (at most 1000 characters); `unit_price_minor >= 0`; `stock >= 0`; `is_active`; timestamps. SKU is trimmed, uppercased, and must match `[A-Z0-9][A-Z0-9_-]{0,63}`. |
| Order | `id` PK; `user_id` FK to User; `status`; `currency = "INR"`; derived `total_minor`; `version` starting at 1 and incremented for each actual status change; timestamps. Owner and lines are immutable after creation. |
| OrderItem | `id` PK; `order_id` FK; `inventory_item_id` FK; `quantity > 0`; immutable `sku_snapshot`, `name_snapshot`, and `unit_price_minor`; derived `line_total_minor`. Unique `(order_id, inventory_item_id)`. |

`currency` is serialized as INR for inventory and order responses. Persist it on Order; the single-currency catalog can derive it. Monetary/stock integers and their arithmetic must fit signed 64-bit storage; reject an operation that would overflow before writing (409 `numeric_overflow`).

~~~mermaid
erDiagram
    User ||--o{ Order : owns
    Order ||--|{ OrderItem : contains
    InventoryItem ||--o{ OrderItem : referenced_by
~~~

Every order has 1-100 distinct inventory items. Users and inventory rows referenced by orders cannot be hard-deleted. Catalog changes cannot rewrite old SKU/name/price snapshots.

### Permitted status transitions

A successful checkout creates `pending` directly and deducts stock at that point. No unpaid draft or payment stage is modeled.

| Current status | Allowed next status | Actor | Stock effect |
| --- | --- | --- | --- |
| pending | processing | admin | None; stock was already deducted. |
| pending | cancelled | admin | Restore every line quantity once. |
| processing | shipped | admin | None. |
| processing | cancelled | admin | Restore every line quantity once. |
| shipped | delivered | admin | None. |
| delivered / cancelled | No different next status | None | None; terminal states. |

Assigning the current status again is a successful no-op: return 200, with no stock change, timestamp/version change, notification, or status event. A different transition absent from the table returns 409 `invalid_order_transition`. Status mutation, version increment, and any stock restoration commit atomically. Serialize concurrent transitions on the order; use the same inventory locking discipline as checkout when restoring stock.

## 3. Business rules and access

### Validation and transactional behavior

1. JSON quantity, stock, and money inputs must be integers, excluding booleans, strings, fractional numbers, and null. Quantities are 1-10000; stock and unit prices are nonnegative. SKU/name normalization occurs before length/uniqueness checks.
2. An order body contains only `items`; each line contains only `inventory_item_id` and `quantity`. Reject empty/oversized orders, duplicate item IDs, unknown fields, and invalid values with 422. A client cannot supply owner, status, prices, totals, or timestamps.
3. Enforce SKU and username uniqueness in database constraints as well as useful service checks. A duplicate catalog SKU returns 409 `duplicate_sku`, including a SKU belonging to a deactivated item.
4. Resolve all order items from authoritative inventory rows. Missing or inactive requested items return 404 `inventory_item_not_found`. Any insufficient quantity returns 409 `insufficient_stock`; no backorders, partial fulfillment, or negative stock.
5. Compute `line_total_minor = quantity * unit_price_minor` and `total_minor = sum(line_total_minor)` on the server from current stored prices. Snapshot those prices during the checkout transaction; later price changes do not reprice orders.
6. Create the order and lines and deduct every quantity in one transaction. A failure rolls back all order/line/stock writes. A success response is sent after commit; success notifications and tracking updates follow commit.
7. In T14, lock inventory rows in ascending ID order with PostgreSQL row locks, then check activity/stock and deduct. Inventory edits, deactivation, checkout, and cancellation must use the same serialization discipline to avoid overselling and lost updates. Confirm behavior against PostgreSQL, including competing requests for the last unit.
8. Admin stock edits assign an absolute count while holding the inventory row lock. Deactivation preserves stock/history and blocks new purchases; cancellation restores stock even if the item is inactive.
9. Owner identity comes from the authenticated, active user. Both active roles can create an order for themselves. Orders cannot be reassigned or edited; only the defined admin status operation changes them.
10. Checkout has no idempotency-key guarantee in this baseline. Repeating a POST can create another order. If the response and order ID are lost, reconciliation requires operator assistance before retrying: this contract has no order lookup by client reference. Automated retry reconciliation needs a later idempotency or lookup extension.

### Authorization matrix

| Resource/action | Anonymous | Active customer | Active admin |
| --- | --- | --- | --- |
| Login; liveness/readiness | Allowed | Allowed | Allowed |
| List/read active inventory | Allowed | Allowed | Allowed |
| Include/read inactive inventory | Denied | Denied | Allowed |
| Create/edit/deactivate inventory | 401 | 403 | Allowed |
| Create order | 401 | For self | For self |
| Read/track order | 401 | Own order only | Any order |
| Change order status | 401 | 403 | Allowed transitions |
| Read password hashes/internal user metadata | Never | Never | Never through public responses |

On catalog and protected routes, a supplied invalid/expired token produces 401, including when catalog access would allow an anonymous caller. Health endpoints do not inspect bearer credentials. An otherwise valid token for an inactive account produces 403. Missing credentials produce 401 on protected routes. All 401 responses include `WWW-Authenticate: Bearer`. Access to another user's order produces 403; a nonexistent order produces 404. Authorize role-only operations before looking up the resource, so customer inventory/status writes consistently return 403.

## 4. Endpoint contract

This section specifies future behavior, not currently implemented routes.

### Transport, validation, and errors

- Business endpoints use `/api/v1`. JSON request/response media type is `application/json`, except the form token request and SSE stream. Protected calls send `Authorization: Bearer <access_token>`; credentials are never accepted in a URL.
- Path IDs must be positive integers (422 otherwise). Valid-but-absent IDs return 404. JSON bodies reject extra fields recursively. PATCH omission preserves a field; explicit null clears only nullable `description`; an empty PATCH is 422.
- 200 returns a successful representation, 201 returns the created resource with `Location`, and 204 has no body. 401 is missing/invalid authentication; 403 is denied access; 404 is absent/hidden inventory or absent order; 409 is a business-state conflict; 422 is invalid input. These meanings follow [HTTP semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15); the specific route choices below are project decisions.
- Domain/HTTP failures initially use `{"detail":{"code":"insufficient_stock","message":"Requested quantity is unavailable."}}`, with a stable code and safe message. Request-validation failures retain FastAPI's structured `{"detail":[{"loc":[...],"msg":"...","type":"..."}]}` shape; never return passwords or tokens in error details. T17 will standardize error envelopes while preserving status codes/authentication headers.
- Unsupported methods return 405 with `Allow`. Unexpected failures return a generic 500 without stack traces or credentials. Readiness failure is 503.

DELETE on an already inactive item returns 204 again. PUT updates an existing item only; SKU, IDs, currency, and timestamps are immutable and excluded from replacement/update input. PUT requires every mutable field, including nullable description; it does not create missing items. Either PUT/PATCH with `is_active=true` can reactivate an item.

`/health` checks the running application; `/health/ready` checks initialized required resources and database connectivity once persistence is added. Before the database stage it checks only resources that the app actually requires. Neither returns connection strings or infrastructure details.

### Inventory query contract

`GET /api/v1/inventory?limit=20&offset=0&sort=id&direction=asc`

| Parameter | Default / allowed values |
| --- | --- |
| limit | 20; integer 1-100. |
| offset | 0; integer >= 0. |
| q | Omitted; if supplied, trimmed length 1-120; case-insensitive literal substring search over name/SKU. |
| in_stock | Omitted means no stock filter; when supplied, `true` selects stock > 0 and `false` selects stock = 0. |
| sort | `id`; enum `id`, `name`, `unit_price_minor`. |
| direction | `asc`; enum `asc`, `desc`. |
| include_inactive | `false`; `true` includes active/inactive rows and requires an admin (anonymous or customer: 403). |

Boolean query parameters accept only literal `true`/`false`; unknown, repeated, or out-of-bounds query parameters return 422. Use ID ascending as a final tie-breaker for name/price sorts. An empty result is 200 with `items: []` and `total: 0`.

### Tracking contract

Use SSE for one-way order status delivery. The browser client will use streaming `fetch` so it can supply a bearer Authorization header; native `EventSource` does not expose an arbitrary-header option. SSE framing and browser API behavior follow the [HTML standard](https://html.spec.whatwg.org/multipage/server-sent-events.html).

- Client sends `Accept: text/event-stream`. Authenticate, verify active account and owner/admin access, and check existence before starting the stream.
- Send an initial `order.snapshot` event, then `order.status_changed` events for committed transitions. Data fields: `order_id`, `status`, `version`, `updated_at`. Use the monotonically increasing order version to detect/ignore duplicate or older messages.
- During T19, register the subscriber before reading the initial snapshot and reconcile queued events by version to avoid a connect-time missed transition. Release the database session before waiting for events.
- Use `Cache-Control: no-cache` and heartbeat comments every 15 seconds; remove subscriptions on disconnect/cancellation. On token expiration close the connection; reconnect with a valid token and recheck account/ownership. Account changes take effect at the next authorization check/reconnect.
- Delivery is live-only, with no event IDs/replay or Last-Event-ID guarantee. Reconnect produces a new current snapshot; intermediate transitions may be missed. A terminal-status snapshot/change is followed by stream closure; clients should stop reconnecting for that terminal order.
- After headers are sent, stream failure closes the connection; it cannot replace the response with a JSON error. The initial broadcaster is process-local and therefore requires one application worker for this guarantee; shared transport is a later extension.

~~~text
event: order.status_changed
data: {"order_id":42,"status":"processing","version":2,"updated_at":"2026-11-07T09:01:00Z"}

~~~
