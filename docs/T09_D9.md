## 3. Diagnosis

For `/t09/blocking-inline`, `time.sleep()` returns control only after it
finishes. Because the call is inside `async def`, it executes on the event-loop
thread. Other tasks cannot run during that interval, so health, async I/O,
timeouts, and already-scheduled callbacks are delayed.

`asyncio.sleep()` yields control. It is a valid replacement for simulated I/O,
but a blocking library cannot be fixed merely by putting it behind `await`.

`asyncio.to_thread()` offloads the blocking call to an AnyIO/default thread
pool. It avoids blocking the event loop but adds thread dispatch and contention.
The synchronous route also uses the AnyIO thread-pool path for FastAPI.

Thread-pool capacity is finite and shared by sync handlers and explicit
offloads. Saturating it adds queueing and can make both slow work and health
endpoints slow. Exact defaults vary by implementation and server configuration,
so capacity should be load-tested rather than assumed.

CPU-intensive Python work should not be repeatedly placed in the event loop or
ordinary thread pool. Processes are the usual separate boundary for CPU
parallelism, and a task queue suits durable or independent jobs. Processes add
serialization, orchestration, memory, and operational trade-offs.

## 4. Context -> mechanism -> trade-off

**Inline blocking.** The symptom is delayed concurrent and health responses.
The mechanism is a synchronous call occupying the event-loop thread. The
trade-off is route simplicity versus blocking every loop task.

**Async-native.** Cooperative sleep/I/O yields control. The trade-off is
requiring dependency support for real async APIs.

**`asyncio.to_thread()`.** The loop stays responsive. The trade-off is bounded
thread capacity and dispatch cost.

**Sync route.** FastAPI offloads ordinary `def` handlers to AnyIO. The
trade-off is similar pool capacity while keeping legacy blocking calls out of
the event loop.

**CPU work.** Worker threads do not add CPU parallelism for GIL-bound Python
code. A separate process or task system is more appropriate, with coordination
and deployment overhead.
