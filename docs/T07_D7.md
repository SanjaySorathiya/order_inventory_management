## 2. `response_model` and response filtering

Return annotations already let FastAPI infer a response model, but an explicit
`response_model=` makes the public contract visible in one place and decouples
it from the handler's internal return type. Routes now declare it explicitly
(`app/api/v1/inventory.py`, `app/api/v1/orders.py`, `app/api/v1/auth.py`).

FastAPI serializes the handler's return value through the response model. Only
declared fields survive, which is the mechanism that keeps private data out of
responses. The exercise verified the exact behavior with a scratch probe before
the tests were written:

| Handler returns | `response_model` | Result | Why |
| --- | --- | --- | --- |
| Dataclass/ORM-style object with extra attributes | `UserRead` (`from_attributes=True`) | 200, extras dropped | Only declared attributes are read. |
| Pydantic model with extra fields | `UserRead` | 200, extras dropped | Declared fields are validated from the instance. |
| `dict` with an extra key (`password_hash`) | `UserRead` (`extra="forbid"`) | **500** | The forbidden key is not silently dropped; response validation fails. |
| `dict` missing a required key | `UserRead` | **500** | The server returned an invalid response. |

Trade-off: the default `extra="ignore"` would silently drop the dict's extra
key, so a leak would never be noticed. Keeping `extra="forbid"` on response
models turns a leak into a visible 500 during development and tests. The price
is that dict returns must match the schema exactly. Prefer returning a storage
object (or ORM row) with `from_attributes=True`, so filtering is the default
behavior rather than a convention.

Nested filtering works the same way. `OrderRead` reads `items` through
`OrderItemRead`, which also has `from_attributes=True`, so each private line field
(`cost_minor`) and the order's `fraud_score` are removed at every level
(`tests/test_t07_response_filtering.py`).

## 3. Invalid client input versus invalid server response

| Question | Failure | Status | Who is at fault | Evidence |
| --- | --- | --- | --- | --- |
| Client sends `username: "ab"` | Request validation (`RequestValidationError`) | 422 with `loc`, `msg`, `type`; input values not echoed | Client | `POST /t07/users/validate` test |
| Handler returns a dict with `password_hash` | Response validation (`ResponseValidationError`) | 500, generic body, no secret in the body | Server | `GET /t07/users-leaky` |
| Handler omits `username` | Response validation | 500 | Server | `GET /t07/users-incomplete` |

A 422 means "fix your request." A 500 caused by response validation means "the
server broke its own contract." Direct callers of the test client see the
underlying `ResponseValidationError`; real clients see only the generic 500.
Server logs should record that exception, since the response body cannot carry it.

## 6. Oral explanation (context -> mechanism -> trade-off)

These paragraphs are the explanation to rehearse aloud. They are written here so they can be checked.

**Request binding and validation.** The ASGI server parses the HTTP request and
passes it to Starlette. FastAPI routing selects the handler. Path, query, header,
cookie, and body parameters are bound from their declared types, and the body is
validated by Pydantic. A failure returns 422 before the handler runs. Mechanism:
declarations define the binding. Trade-off: strict types catch bad input early,
but they must be paired with explicit business rules, such as stock checks, in the
service layer.

**Response filtering.** After the handler returns, FastAPI validates the value
against `response_model` and serializes only the declared fields. Mechanism:
`from_attributes=True` lets the model read attributes from storage objects, and
`extra="forbid"` makes a leaked or missing field a server error rather than a silent
change. Trade-off: forbidding extras on response models catches leaks, but it makes
dict returns brittle, so storage objects are the safer default.

**ASGI versus WSGI.** WSGI is a synchronous call interface where each request
typically occupies a worker thread or process. ASGI is an async interface that can
multiplex waiting I/O, supports WebSockets and streaming, and runs `async def`
handlers on the event loop. ASGI does not make blocking code non-blocking: a
synchronous call inside an `async def` handler still stalls the loop. Trade-off:
ASGI handles more concurrent I/O-bound connections per process, but its benefits
depend on non-blocking application code and on the deployment's worker model
(T08-T10, T21).
