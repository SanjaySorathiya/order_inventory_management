## 2. Router composition

~~~text
app/main.py                 # app factory, fresh store, /health
app/api/deps.py             # store dependency, duplicate queries, production guard
app/api/errors.py           # safe structured validation errors
app/api/v1/__init__.py      # versioned router composition
app/api/v1/auth.py          # /auth, Auth tag
app/api/v1/inventory.py     # /inventory, Inventory tag
app/api/v1/orders.py        # /orders, Orders tag
app/schemas/inventory.py    # create/replace/patch/read/page/query
app/services/inventory.py  # temporary storage and inventory operations
exercises/t03_parameters.py # isolated ASGI app
~~~

**How does APIRouter help?** Each module owns its routes. The versioned router
includes the resource routers; create_app() includes the versioned router.
Combining /api/v1 and /inventory produces /api/v1/inventory. Tags organize
documentation and do not enforce permissions. See
[FastAPI router composition](https://fastapi.tiangolo.com/tutorial/bigger-applications/).

The store lives on application.state. Two app factories create independent
stores. A short lock protects mutations between synchronous handlers. This is
not evidence of PostgreSQL locking or multi-worker consistency.

## 3. HTTP methods and body semantics

| Method/path | Meaning | Success |
| --- | --- | --- |
| GET /api/v1/inventory | Filter, sort, then paginate active items. | 200 InventoryPage |
| GET /api/v1/inventory/{item_id} | Read an active item. | 200 InventoryRead |
| POST /api/v1/inventory | Create with normalized SKU/name. | 201 with Location |
| PUT /api/v1/inventory/{item_id} | Replace every mutable field on an existing item. | 200 InventoryRead |
| PATCH /api/v1/inventory/{item_id} | Change a nonempty subset of mutable fields. | 200 InventoryRead |
| DELETE /api/v1/inventory/{item_id} | Deactivate while retaining SKU, history, and stock. | 204, empty body |

PUT requires name, description, unit_price_minor, stock, and is_active.
Description is required but nullable. PUT does not create missing items.

PATCH omission preserves state; explicit null clears only description. Empty
PATCH and null for other mutable fields return 422. model_dump(exclude_unset=True)
preserves omission versus explicit input. See
[FastAPI body updates](https://fastapi.tiangolo.com/tutorial/body-updates/).

SKU, ID, currency, and timestamps are excluded from replacement/patch input.
Extra body fields are rejected. Money/stock must be nonnegative signed 64-bit
integers; booleans, strings, fractional numbers, and null are rejected using
Field(strict=True). See
[Pydantic field constraints](https://docs.pydantic.dev/latest/concepts/fields/).

**Is DELETE idempotent?** Repeated deletion returns 204 without changing stock
or updating the inactive item's timestamp again. A missing ID returns 404.
Deactivated SKUs remain reserved; duplicate normalized SKU returns 409.

## 4. Paths, filtering, sorting, and pagination

Inventory/order IDs use Annotated[int, Path(gt=0, le=MAX_INT64)]. Noninteger,
nonpositive, or oversized IDs return 422. Valid absent inventory IDs return 404.
Pending order routes validate IDs before returning 501.

InventoryQuery binds through Query() and rejects unknown names. A dependency
rejects repeated scalar query parameters, including identical repetitions.
See [FastAPI query models](https://fastapi.tiangolo.com/tutorial/query-param-models/).

| Parameter | Default | Contract |
| --- | --- | --- |
| limit | 20 | Integer 1-100. |
| offset | 0 | Integer >= 0. |
| q | Omitted | Trimmed length 1-120; case-insensitive literal name/SKU substring. |
| in_stock | Omitted | Literal true selects positive stock; false selects zero stock. |
| sort | id | id, name, unit_price_minor. |
| direction | asc | asc, desc. |
| include_inactive | false | Literal true/false; true currently returns 403 pending admin auth. |

Boolean query values are case-sensitive true/false strings. Values 1, yes,
and True return 422. Percent signs/underscores in q are literal characters.

Count filtered results before pagination. Sort before slicing. Name sorting
currently uses Python string order. Equal names/prices retain ID ascending,
including when primary direction is descending. No matches produce items: []
and total: 0; an offset beyond the end retains the filtered total.

## 5. Required, optional, and nullable queries

| Declaration in the exercise | Required? | Omission |
| --- | --- | --- |
| required: Annotated[str, Query(min_length=1)] | Yes | 422 |
| required_nullable: Annotated[str &#124; None, Query()] | Yes | 422 |
| optional_nullable: Annotated[str &#124; None, Query()] = None | No | Python None |

**Does nullable mean optional?** No. A default allows omission; the annotated
type describes values. These are independent decisions.

HTTP query strings contain text. required_nullable=null supplies the string
"null"; optional_nullable= supplies an empty string. Neither is JSON null.
The inventory body description demonstrates actual null versus omission.

~~~sh
uv run --locked uvicorn exercises.t03_parameters:app --port 8001 --reload
~~~

Visit /parameters?required=hello&required_nullable=world on port 8001, or /docs.
Omitting either required query gives a structured validation error.

The exercise registers /items/search before /items/{item_id}. Routing selects
the first matching route. If dynamic comes first, "search" is captured and
integer validation returns 422; routing does not retry the static handler.
The intentionally reversed ordering exists only in a test. The main API does
not import the exercise app or gain extra contract endpoints.

## 6. Errors and pending workflows

Domain errors use detail.code/detail.message. Validation errors retain detail
entries with loc, msg, and type. Submitted values and validator context are
omitted so rejected password/token fields are not echoed. T17 will extend the
overall error handling contract.

Auth /token and the four order operations return 501. They issue no tokens,
create no orders, and return no invented successes. Form login is scheduled
for T15; the events placeholder does not start SSE. Readiness remains planned.

## 7. Run and demonstrate the main API

~~~sh
uv run --locked uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
~~~

Inspect the four tags in /docs. On a fresh development instance, this PowerShell
sequence exercises all five methods:

~~~powershell
$inventoryUrl = "http://127.0.0.1:8000/api/v1/inventory"
$item = Invoke-RestMethod -Method Post -Uri $inventoryUrl -ContentType "application/json" -Body '{"sku":"KB-001","name":"Keyboard","unit_price_minor":12500,"stock":5}'
$itemUrl = "$inventoryUrl/$($item.id)"

Invoke-RestMethod -Uri $itemUrl
Invoke-RestMethod -Uri "${inventoryUrl}?q=keyboard&in_stock=true&limit=1"
Invoke-RestMethod -Method Put -Uri $itemUrl -ContentType "application/json" -Body '{"name":"Mechanical Keyboard","description":null,"unit_price_minor":15000,"stock":8,"is_active":true}'
Invoke-RestMethod -Method Patch -Uri $itemUrl -ContentType "application/json" -Body '{"stock":3}'
Invoke-RestMethod -Method Delete -Uri $itemUrl
Invoke-RestMethod -Method Delete -Uri $itemUrl
Invoke-RestMethod -Method Patch -Uri $itemUrl -ContentType "application/json" -Body '{"is_active":true}'
Invoke-RestMethod -Uri $itemUrl
~~~

Repeating the initial POST against the same store returns 409; use a new SKU
or restart. Reload also clears inventory, so avoid code edits during the demo.
